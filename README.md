# 基于大模型的智能文档问答系统 (RAG-based Document QA)

这是一个基于大语言模型（LLM）的本地文档问答系统。
项目经历了**“原生手搓链路 -> 引入向量检索 -> 框架与底层算法复现”**的完整演进过程。不仅实现了基础的 RAG 问答，还针对“切块截断”、“中文语义丢失”、“网络抖动”等工程痛点进行了深度优化与复盘。

## 📌 核心功能 (Features)

- [x] **原生 RAG 链路**：手写实现文档读取、文本分块、Prompt 拼装与大模型 API（DeepSeek）调用。
- [x] **工程化防御**：引入 `try...except` 异常处理，实现 API 超时重试（最大 3 次）与降级兜底策略，防止服务崩溃。
- [x] **语义检索升级**：引入 `LangChain` 与 `FAISS` 向量库，将传统的“关键词匹配”升级为“向量语义检索”，大幅提升长文本检索准确率。
- [x] **中文模型优化**：替换英文 Embedding 模型，采用针对中文优化的 `BAAI/bge-small-zh-v1.5`，成功解决多实体长文本检索失败的问题。
- [ ] **服务化与交互**：基于 FastAPI 封装后端 RESTful API，结合 Gradio 实现 Web 交互与流式输出。（🚧 规划中）

## 🛠️ 技术栈 (Tech Stack)

- **语言**：Python 3.11+
- **大模型**：DeepSeek API (兼容 OpenAI SDK)
- **RAG 框架**：LangChain
- **向量检索**：FAISS (向量存储) + BAAI/bge-small-zh-v1.5 (Embedding)
- **后端与前端**：FastAPI / Gradio (规划中)

## 🧠 踩坑日记与架构思考 (Engineering Notes)

> 详细的心路历程见 [DEVLOG.md](./DEVLOG.md)，以下为核心痛点的技术复盘。

### 1. 手写切块算法：边界爆炸与重叠（Overlap）机制
- **痛点**：初期使用 `range` 进行 500 字硬切，导致关键语句被从中间截断，大模型因缺失上下文而出现幻觉。
- **探索**：为了搞懂底层逻辑，尝试用原生 Python 手写带“分隔符优先级”和“重叠（Overlap）”的切块函数。
- **冲突**：在手写过程中遇到了**“边界爆炸”**问题——当把上一块的结尾（Tail）拼接到新块开头时，总长度极易超过设定的 `chunk_size` 上限。
- **解决**：必须在拼接前动态计算可用空间（`chunk_size - len(tail)`），对新文本进行动态截断。
- **感悟**：通过手写踩坑，彻底理解了 LangChain 中 `RecursiveCharacterTextSplitter` 底层递归切分的精妙之处。

### 2. 中文语义丢失与 Embedding 模型的替换
- **痛点**：在测试长文本多实体问答（如“XX的兄弟姐妹叫什么”）时，模型频繁回答“不知道”。
- **排查**：发现两个原因。一是 Top-K 设置过小；二是默认的开源小模型（`all-MiniLM-L6-v2`）为英文模型，对中文语义理解极差（无法关联“兄弟姐妹”与“哥哥/弟弟”）。
- **解决**：将 Embedding 模型替换为中文优化的 `BAAI/bge-small-zh-v1.5`，并调整检索策略。成功召回分散在不同段落的相关实体，大幅降低拒答率。
- **感悟**：RAG 系统的上限并不完全由大模型决定，**“检索质量”直接决定“生成质量”**。

### 3. API 网络抖动与防御性编程
- **痛点**：调用外部大模型 API 时，极易受网络波动影响导致脚本直接崩溃。
- **解决**：加入 `timeout=10` 超时控制，配合 `for` 循环与 `try...except` 实现重试机制。若连续 3 次失败，则执行降级策略，返回友好的兜底提示，保障程序鲁棒性。
