# 基于大模型的智能文档问答系统 (RAG-based Document QA)

这是一个基于大语言模型（LLM）的本地文档问答系统。
项目经历了**“原生手搓链路 -> 引入向量检索 -> 前后端分离全栈化”**的完整演进过程。不仅实现了基础问答，还针对“切块截断”、“中文语义丢失”、“网络抖动”、“API异常”等工程痛点进行了深度优化，具备生产级雏形。

## 📌 核心功能 (Features)

- [x] **全栈工程架构**：基于 FastAPI 构建 RESTful 后端接口，结合 Gradio 搭建 Web 前端交互界面，实现前后端分离。
- [x] **语义检索升级**：引入 LangChain 与 FAISS 向量库，替换为中文优化的 `BAAI/bge-small-zh-v1.5` Embedding 模型，解决多实体长文本检索失败的痛点。
- [x] **高可用与容错设计**：实现 API 调用的超时控制、基于异常分类的重试机制（指数退避）与优雅降级策略（如认证失败时直接返回检索原文）。
- [x] **成本实时监控**：打通大模型 Token 用量统计，实现单次请求成本与系统累计成本的实时追踪。
- [ ] **多租户数据隔离**：引入 SQLite 数据库，实现基于 `user_id` 的历史记录持久化与隔离。（🚧 规划中）
- [ ] **混合检索与重排**：引入 Rerank 机制，解决纯向量检索对专有名词召回不准的问题。（🚧 规划中）

## 🛠️ 技术栈 (Tech Stack)

- **语言**：Python 3.11+
- **大模型**：DeepSeek API (兼容 OpenAI SDK)
- **RAG 框架**：LangChain
- **向量检索**：FAISS + BAAI/bge-small-zh-v1.5
- **后端服务**：FastAPI + Uvicorn + Pydantic (数据校验)
- **前端展示**：Gradio
- **代码结构**：模块化解耦（`main.py` 路由层 / `rag_core.py` 核心业务类 / `schemas.py` 数据模型）

## 🧠 工程踩坑与架构思考 (Engineering Notes)

> 详细的心路历程见 [DEVLOG.md](./DEVLOG.md)，以下为核心痛点的技术复盘。

### 1. 手写切块算法：边界爆炸与重叠（Overlap）机制
- **痛点**：初期使用固定字数硬切，导致关键语句被从中间截断，大模型因缺失上下文而出现幻觉。
- **解决**：手写基于“分隔符优先级（段落->句号->硬切）”和“重叠（Overlap）”的切块逻辑。并在拼接时通过动态计算空间（`chunk_size - len(tail)`）解决了“边界爆炸”问题。
- **感悟**：通过手写踩坑，彻底理解了 LangChain 中 `RecursiveCharacterTextSplitter` 底层递归切分的精妙之处。

### 2. 中文语义丢失与 Embedding 模型的替换
- **痛点**：测试长文本多实体问答时，模型频繁回答“不知道”。原因是默认开源小模型（`all-MiniLM-L6-v2`）对中文语义理解极差。
- **解决**：将 Embedding 替换为 `BAAI/bge-small-zh-v1.5`，成功召回分散在不同段落的相关实体，大幅降低拒答率。

### 3. API 防御性编程与异常分类降级
- **痛点**：大模型 API 极易受网络波动、限流影响，且可能因配置错误（如 Key 失效）导致系统崩溃。
- **解决**：引入了分类捕获机制：
  - 针对 `APITimeoutError` / `RateLimitError`：采用**指数退避（Exponential Backoff）**进行重试。
  - 针对 `AuthenticationError`：直接触发熔断与**优雅降级**（返回本地检索到的 Top-K 原文）。
  - 针对其他未知异常：保障程序不崩溃，并给出友好提示。
